# TripMaker — Task Breakdown to Baseline

This file breaks [PLAN.md](PLAN.md) down into small tasks. **Each task is one commit.** Do them in order. Each task leaves the app building, linting and passing its tests.

> **For Claude Code:** Do one task at a time. Before committing, run `npm run lint`, `npm run typecheck` and `npm test` (plus `npm run test:e2e` once it exists). Use the commit message given in the task. If a task turns out larger than expected, split it and say so. Do not combine tasks.

## What "baseline" means

The baseline is the core loop working end to end, by several people at once:

> Create a trip → others join with the code → everyone adds wishes → everyone reacts → host generates a plan → everyone sees the plan and the heads-up warnings.

That covers **Phases 1–5** of PLAN.md, plus the Playwright smoke test from Phase 7, which proves the loop works, plus a first deploy to Cloudflare so people can use it from their own phones. Journal mode, rejoin links, drag-and-drop and the polish pass come after the baseline (see the end of this file).

**Dependencies to confirm before starting** (PLAN.md says to ask before adding anything outside the Tech Stack):
- `@opennextjs/cloudflare` + `wrangler` (dev): run Next.js on Cloudflare Workers and manage D1.
- `@prisma/adapter-d1`: lets Prisma 7 talk to D1.
- `tsx` (dev): runs `prisma/seed.ts`.
- No drag-and-drop library for the baseline. Slots are moved with a "Move to…" picker instead (T29).

### Database setup

- **Engine:** Cloudflare D1 (SQLite), database name `tripmaker`, bound as `DB` in `wrangler.jsonc`. Locally, wrangler keeps it in `.wrangler/state`, which `next dev`, `npm run preview` and the seed script all share. Gitignore `.wrangler/` and `.dev.vars`.
- **Prisma:** v7 with `provider = "sqlite"` and `@prisma/adapter-d1`. Follow Prisma's Cloudflare D1 guide for the generator and `prisma.config.ts`. D1 support is in Preview, so check the guide rather than older blog posts.
- **Schema:** copy Section 3 of PLAN.md exactly. Add `@@index([tripId])` to `Wish` and `PlanSlot`, and `@@index([wishId])` to `Reaction`. These are harmless on SQLite and help on Postgres.
- **Enums:** Prisma supports enums on SQLite from v6.2, so the schema moves to Postgres unchanged. Don't use any SQLite-only features (raw SQL, `@db.*` native types).
- **Client per request** (`lib/db.ts`): on Workers the D1 binding belongs to the request, so there's no global singleton. `getDb()` reads `getCloudflareContext().env.DB` and returns `new PrismaClient({ adapter: new PrismaD1(env.DB) })`. Wrap it in React's `cache()` so one request reuses one client.
- **No transactions:** D1 ignores Prisma's `$transaction` (both forms) and runs each query on its own. Order multi-step writes so that stopping halfway leaves the data valid or easy to repair (see T09 and T26).
- **Version bumping:** `bumpVersion(db, tripId)` in `lib/db.ts` runs `trip.update({ data: { version: { increment: 1 } } })`. Every route that writes to a trip calls it last, so pollers see the change.
- **Migrations** (no `prisma migrate dev` on D1):
  1. `wrangler d1 migrations create tripmaker <name>` makes an empty numbered SQL file in `migrations/`.
  2. `prisma migrate diff` writes the SQL into it: `--from-empty` for the first migration, `--from-local-d1` after that, always `--to-schema prisma/schema.prisma --script`.
  3. `wrangler d1 migrations apply tripmaker --local` (or `--remote` for production).

  Commit `migrations/`.
- **Seed:** `prisma/seed.ts` runs with `tsx`. It gets the local `DB` binding from wrangler's `getPlatformProxy()`, builds a Prisma client from it, then wipes and recreates a fixed demo trip with code `DEMO42`. Make it deterministic: use hard-coded data or a seeded PRNG, never `Math.random()`, so planner integration tests can rely on it.
- **Scripts:**
  - `db:migration:new`: steps 1–2 above.
  - `db:migrate:local`, `db:migrate:remote`: step 3.
  - `db:seed`: `tsx prisma/seed.ts`.
  - `db:reset`: delete `.wrangler/state`, run `db:migrate:local`, then `db:seed`.
  - `db:query`: `wrangler d1 execute tripmaker --local --command`, for quick checks like `npm run db:query -- "SELECT * FROM Trip"`. This replaces Prisma Studio, which can't open D1.
- **E2E database:** Playwright serves the built Worker with `wrangler dev --persist-to .wrangler/e2e` and applies migrations into that folder first, so tests never touch your dev data.
- **Tokens never leave the server:** `Member.token` is only read in `lib/auth.ts`. Every query that builds API output uses an explicit `select` that leaves `token` out.

### Backend setup (route handlers)

**Identity.** Each trip gets its own cookie, `tm_<CODE>`, holding the member's `token`. It is `httpOnly`, `sameSite: "lax"`, `path: "/"`, kept for one year, and `secure` in production. Because the cookie is per trip, one browser can be in several trips at once.

**`lib/auth.ts`**
- `setMemberCookie(code, token)`
- `getCurrentMember(code)`: reads the cookie and looks up the Member by token **and** by trip code. Returns `null` if either doesn't match.
- `requireMember(code)`: returns `{ trip, member }`, or throws a 404 if the trip doesn't exist / 401 if the caller isn't a member.
- `requireHost(code)`: same as `requireMember`, plus a 403 if the member isn't the host.

**Handler pattern** (every route stays this thin):

```ts
// app/api/trips/[code]/wishes/route.ts
export async function POST(req: Request, { params }: { params: Promise<{ code: string }> }) {
  return handle(async () => {
    const { code } = await params;                 // params is a Promise in Next 15+
    const db = getDb();
    const { trip, member } = await requireMember(code);
    const input = createWishSchema.parse(await req.json());
    const wish = await db.wish.create({ data: { ...input, tripId: trip.id, authorId: member.id } });
    await bumpVersion(db, trip.id);
    return json({ id: wish.id }, 201);
  });
}
```

`handle()` in `lib/http.ts` turns errors into responses:
- `ZodError` → 400 `{ error: "Invalid input", details }`
- `HttpError(status, msg)` → that status
- anything else → 500

The response shape is always `{ error: string }`.

**Next.js 15+ gotchas:** `params` and `cookies()` are both async, so always `await` them.

**State endpoint.** `GET /state?since=<version>` first reads only the Trip row. If `trip.version` equals `since`, it returns `{ unchanged: true }` (1 row read instead of ~300, which keeps 10 people polling every 5 s inside D1's free tier). Otherwise it returns one `TripState` object:

```ts
type TripState = {
  trip: { code, name, destination, startDate, endDate, phase, days };
  meId: string;
  members: { id, name, color, isHost }[];         // no tokens
  wishes: (WishDTO & { reactions: { memberId, value }[] })[];
  slots: { id, wishId, dayIndex, timeOfDay, track, pinned }[];
  warnings: Warning[];
  version: number;                                // Trip.version — the client sends it back as ?since=
};
```

Warnings are **not stored** in the database. The state endpoint recomputes them each time by calling `detectWarnings()` from the planner on the current slots. They're cheap to compute for 10 people and never go stale.

### Frontend setup

- **Server/client split:**
  - `app/t/[code]/page.tsx` is a server component. It checks the cookie and, for a member, calls `buildTripState()` **directly** (no HTTP round trip) and renders `<TripApp initialState={…} />`.
  - Someone without a valid cookie sees `<JoinForm code={code} />` instead.
- **Polling** (`useTripState(code, initial)`):
  - Uses `setInterval` every 5 s with `fetch(…/state?since=<current version>, { cache: "no-store" })`.
  - Pauses while `document.hidden`.
  - Exposes `refresh()` so every mutation can refetch right away.
  - Ignores `{ unchanged: true }`, and only replaces state when it gets a full `TripState`.
- **Polling never touches forms.** Form components keep their own `useState`, seeded once from props. They are never keyed on `version` and never re-derive from polled data, so an open form survives every poll.
- **Optimistic reactions:** set the new value locally, PUT it, and roll back if the request fails.
- **Tabs:** set by a `?tab=wishes|plan|headsup|group` search param, so links and the back button work. On mobile they're a horizontal tab bar under the header.
- **Member colors:**
  - A fixed palette of 10 hex values in `lib/colors.ts`.
  - Render colors with inline `style={{ backgroundColor }}`. Tailwind can't generate dynamic class names.
  - Never show color alone: always pair it with the name or initial.
- **Components** (one per file): `StartTripForm`, `JoinTripForm`, `TripApp`, `TabBar`, `MemberDot`, `MemberList`, `ShareCode`, `WishBoard`, `WishCard`, `WishFilters`, `WishForm`, `ReactionButtons`, `ReactionAvatars`, `PlanView`, `DayTabs`, `TimeBlock`, `SlotCard`, `MoveSlotPicker`, `HeadsUp`, `FairnessChecklist`.

## Phase 4 — Planner engine (pure, no DB)

Planner inputs are **planner-specific types**, not Prisma models, so the module never imports `@prisma/client`:

```ts
type PlannerMember = { id: string };
type PlannerWish = {
  id; authorId; kind; priority; timeOfDay; durationHrs; costLevel; energy;
  title; notes; createdAt: Date;
  reactions: { memberId: string; value: "IN" | "MAYBE" | "SKIP" }[];
};
type PlanSlotDraft = { wishId; dayIndex; timeOfDay; track: "GROUP" | "SPLINTER"; pinned: boolean };
```

**Interpretations to settle now** (PLAN.md leaves these open):
- **Ties:** sort by score (descending), then `createdAt` (ascending), then `id` (ascending).
- **Long wishes:** a wish longer than 4 h produces **two `PlanSlot` rows** (same `wishId`) in adjacent blocks on the same day.
- **Splinters alongside a group activity:** a splinter can share a block with the group activity only if none of the splinter's IN members are IN (or the author of) that block's group activity or another splinter in that block.
- **Rest block:** "at least one free block per day" means a block with **no slots at all**.
- **Budget conflict:** a day's cost is the sum of `costLevel` over the slots the constrained member is IN on that day.
- **ANY time of day:** these wishes are placed after the wishes with a fixed time, in block order MORNING → AFTERNOON → EVENING → NIGHT → EARLY_MORNING.
- **Packing:** fill days in order, one wish at a time.

### T20 · Scoring + classification
- `score.ts`: `inSet(wish)` (the author plus every IN reaction, with the author's own reaction ignored), `support()`, `score()` and `classify(wish, memberCount)` → `GROUP | SPLINTER | SOLO`.
- Tests:
  - The group threshold for 10 members is 6, and for 3 members it's 2.
  - MAYBE counts 0.5.
  - The priority weights are applied.
  - CONSTRAINT wishes are excluded.
- **Commit:** `feat(phase-4): planner scoring and classification`

### T21 · Group placement
- `place.ts`: build an empty grid of `days × 5`, then:
  1. Apply the pinned slots.
  2. Place GROUP wishes by score into their preferred block, or any free block if `ANY`.
  3. Use two adjacent blocks for wishes over 4 h.
  4. Allow at most one `energy ≥ 3` group activity per day.
  5. Leave a rest block every day.
- Group wishes that can't be placed go to `unscheduled`.
- Tests:
  - Pinned slots are never moved.
  - There's one group activity per block.
  - Long wishes take two blocks.
  - Energy is capped.
  - Every day has a free block.
- **Commit:** `feat(phase-4): planner group placement`

### T22 · Splinter + solo placement
- Place SPLINTER wishes, then SOLO ones, using the "alongside" rule above.
- Tests:
  - A splinter never overlaps its members' group activity.
  - SOLO wishes come after SPLINTER ones.
  - The rest block stays empty.
- **Commit:** `feat(phase-4): planner splinter placement`

### T23 · Fairness pass
- `fairness.ts`: for each member without a scheduled MUST, try swapping their best MUST into the slot of the lowest-scoring item it fits. Don't touch pinned slots, and don't remove another member's *only* scheduled MUST.
- Tests:
  - A swap happens.
  - A swap is refused when it would break someone else's MUST.
  - When no swap is possible, the member is reported for the warning.
- **Commit:** `feat(phase-4): planner fairness pass`
